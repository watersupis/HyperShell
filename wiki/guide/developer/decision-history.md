# 历史决策摘要

本页从已归档设计稿中提炼对维护当前系统仍有帮助的决策背景。设计稿日期、批准状态和实现计划只描述当时状态；此页不是当前路线图。当前行为以源码、manifest、schema 和测试为准。

## 插件与宿主边界

历史模块化设计强调把单一功能的界面、策略、专属状态和测试放在功能所有者一侧；宿主只提供多个功能共同需要的受控能力。UI 插槽是布局/贡献契约，不是授权机制；插件能力仍须经 manifest 授权和运行时 RPC 校验。此原则仍适用于新增功能，但具体目录和 API 以[架构地图](./architecture)及[插件 API](./plugin-api)为准。

## SFTP 数据完整性

2026 年 8 月的 SFTP 评审把关注点归为数据完整性、任务所有权、失败可见性和可恢复性：冲突不能被 UI 状态隐藏；文本编辑要识别无法安全往返的数据；写入需要考虑原子替换和远端并发修改；同步任务应能辨认所属会话，关闭视图不能静默丢弃进行中的工作；远端变更失败需要反馈。该评审也提醒不要只按暗色主题判断对比度，需覆盖多主题及键盘/结构可访问性。

这些是审查和测试的维度，不是对当前每种传输/服务器组合的保证。实现变化时应检查 SFTP transport、IPC、编辑器和传输队列，并以回归测试及实际协议行为验证。

## 终端标题与进程观测

2026 年 8 月的标题设计区分 shell 报告的标题（例如 OSC 标题）与本地进程树推断的前台程序名：两者来源和可信边界不同，不应把本地观察逻辑当成远程 SSH 进程检测。标题更新应按会话隔离，避免一个会话的进程状态污染另一个标签；轮询器也应随会话生命周期释放。标题规则应有稳定优先级，并覆盖 shell 提示符、前台 CLI 和运行恢复状态之间的切换。

当前事件、标题优先级和平台可用性需从 session-core、桌面进程观测实现及其测试核对，不以旧设计稿中的实现清单为准。

## 本地 Shell 安全与兼容

2026 年 8 月的本地 Shell 设计采用“renderer 只传 profile ID，主进程从持久化配置解析可执行文件、参数和工作目录”的边界，避免 renderer 任意指定本机程序。启动环境需剔除 Electron/Node 注入变量，以免 shell 内的 Node 工具继承宿主运行时选项；用户配置的环境变量仍是显式覆盖入口。已检测到的 profile 重新扫描时保留用户编辑，仅更新可用状态；隐藏检测项而非删除，避免下次扫描又出现。

管理员权限不能在普通权限窗口中安全承载同一 ConPTY，因此提升权限的设计采用独立提升实例，并且命令行只传 profile ID，不传 executable/args/cwd。该边界只适用于 Windows 提升流程；具体实现和平台限制以当前代码为准。

## 终端渲染诊断

2026 年 8 月的一次 TUI 残影调查先用已重建的 Electron 运行态验证，证伪了 WebGL、画布透明度和强制重绘假设；调整窗口尺寸会触发完整重绘，但这本身不是根因。随后检查发现强制 `convertEol` 会改变 PTY 的换行/光标语义。可复用的经验是先固定真实运行产物和复现输入，再一次只改一个变量；对终端协议字节流应尊重 PTY 的行结束语义，不用渲染补丁掩盖状态错误。具体 xterm 配置与回归行为要以当前实现及测试确认。

## 自动更新与发布顺序

2026 年 5 月的更新方案选择通知后由用户确认安装，而非静默自更新；并记录了发布元数据与安装工件的依赖：客户端不应先看到指向尚未上传工件的更新元数据。此约束在采用相同发布协议时仍有价值；平台支持、签名要求、首次安装限制和具体文件顺序必须以当前发布工作流、Electron Builder 配置和更新服务复核。
